# leanerVM

Lean 4 proofs about [leanVM](https://github.com/leanEthereum/leanVM): its verifier, and the signature schemes and data-availability scheme its aggregation guest checks. The proof projects are leanVM's `formal/` at the commit in [`leanvm-rev`](leanvm-rev) (branch `FV`), with their history.

**What is proved is in [`Statement/`](Statement/README.md), and a reviewer reads that folder only**: eleven files of definitions and end statements (its README lists them in reading order, with the end theorems and where they are proved), the generated guest bytecode, and proved `@[csimp]` lemmas that only make the compiled definitions fast (`Statement/Fast/`). It imports Mathlib, VCVio and CompPoly, nothing of the proofs (CI checks it). Everything else is proof, each end theorem's statement a proposition of `Statement/` and its axioms Lean's three:

| Path | What it proves |
| --- | --- |
| [`Statement/`](Statement/README.md) | nothing: the statement every other project proves, definitions and end statements only |
| [`lean_vm/`](lean_vm/README.md) | leanVM's verifier at `main` (`94ee12ff`, the `keccak-gkr` branch merged, and the machine halting in the final state `(pc, fp) = (g^(N-1), 1)`: Keccak-256 hashing, a Keccak-f[1600] duplex sponge for Fiat-Shamir, the `KECCAK` instruction proved by GKR over the rounds), knowledge sound with a fixed straight-line extractor (a deterministic algorithm, list decoding by Guruswami–Sudan; its polynomial running time is read off its loops, not a theorem), and complete, in the random-permutation model: Keccak-256 and Keccak-f[1600] built from one random permutation `π`, which the adversary queries forward and inverse (`LeanVM.knowledgeSoundness_holds`, `LeanVM.completeness_holds`; knowledge soundness at most `(Q + 2^14) · 2^-128 + 7 (Q + 2^14)² · 2^-256` for `Q ≤ 2^128` permutation queries, completeness at most `2^-127` at `2^25` nonces per proof of work). The aggregation guest is knowledge sound with its witness named, read off the execution's memory (`LeanVM.Guest.End.guest_knowledge`, `decode_binds`, and in the random-permutation model `aggregate_sound_outer`), and complete within an explicit budget linear in a node's work, each child charged by its announced stack log and rate (`LeanVM.Guest.Budget.guest_complete`), which covers every node of up to 16 children (the guest's `MAX_RECURSIONS`, at every stack log and rate a child announces) and 2048 declared claims, coverage slots and children's claims, holding no signature or blob directly, and every leaf of up to 2048 raw signatures, declared claims and coverage slots (`guest_complete_recursion`, `guest_complete_leaf`), and further recursion nodes of up to 8 children and 2^15 claims, mixed nodes of up to 4 children and 1024 raw signatures, and nodes checking a blob of up to 8 rows (`guest_complete_covered`). Its honest proofs chain: in the random-permutation model the honest proof of a guest execution is rejected, by the verifier also refusing a zero challenge where the guest divides, with probability at most `2^-126`, and with the deployed Keccak, wherever that verifier accepts it, it meets every hypothesis the guest's completeness assumes of a child (`guest_child_complete`). The recursion step, the batching of a node's children's deferred claims, is sound in the random-permutation model: at most `(QA + QV + 1) · 2^-191 + 5 (QA + QV)² · 2^-256` for `QA ≤ 2^128` queries of the adversary and `QV ≤ 2^96` of the batching (`LeanVM.Guest.Batch.batch_sound_holds`). This is the batching run outside the circuit with Keccak-f[1600] = `π`; it does not compose with the guest's in-circuit statements, which use the deployed Keccak-f[1600], so soundness across recursion levels does not follow from it: see [`lean_vm/README.md`](lean_vm/README.md#the-guests-proof) |
| [`common/`](common/README.md) | the proofs the projects share, about the random-permutation model (a uniform permutation π with π and π⁻¹ queries, defined in `Statement/`): the indifferentiability of the Keccak-256 sponge from a random oracle (q²/2^509), and the transfer of random-oracle bounds to the random-permutation model, for Keccak-256 alone and with direct permutation calls in leanVM's duplex (q²/2^508) |
| [`lean_xmss/`](lean_xmss/README.md) | leanXMSS's SUF-CMA security in the random-permutation model, `(Q + 1) · 2^-127` for `1 ≤ Q ≤ 2^128` permutation calls (`XmssSecurity.leanXmss_rpm_security`), from its 127 bits in the random-oracle model (`XmssSecurity.leanXmss_has_127_bits_of_classical_security`, a step of the proof) |
| [`lean_sphincs/`](lean_sphincs/README.md) | leanSPHINCS's SUF-CMA security in the random-permutation model, `(Q + 1) · 2^-127` for `1 ≤ Q ≤ 2^128` permutation calls, at every proved lifetime (`Sphincs.Lifetimes.requestedSecurityRpm`), from its 127 bits in the random-oracle model (`Sphincs.Lifetimes.requestedSecurity`, a step of the proof) |
| [`lean_da/`](lean_da/README.md) | LeanDA's completeness, position binding and code binding: Benedikt Wagner's framework and proofs ([b-wagn/fv-pq-da](https://github.com/b-wagn/fv-pq-da), [his post](https://ethresear.ch/t/formally-verified-security-for-pq-das-leanda/25746)), ported and instantiated with LeanDA, and moved to the random-permutation model: perfect completeness for every permutation (`LeanDa.leanDa_perfectlyComplete_rpm`), position binding `(Q + 1)² · 2^-256` for `Q ≤ 2^128` (`LeanDa.leanDa_positionBinding_rpm`) and code binding conditional on the argument's knowledge soundness in the random-permutation model: for an argument with knowledge-soundness error `(q + c) · 2^-k`, code binding `(Q + c + 2^22) · 2^-k + (Q + 2^20) · 2^-93 + (Q + 2^22)² · 2^-158` (`LeanDa.leanDa_codeBinding_rpm_bound`) for `Q ≤ 2^127` permutation calls and `r ≤ 1024` rows. Wagner's two collision terms are birthday bounds, proved here; his knowledge-soundness term is read back as the argument's knowledge soundness in the random-permutation model, which holds only for an argument that has, or simulates, access to the permutation; an argument complete for every permutation does not, so completeness and code binding are not both meaningful for one argument, as in Wagner's random-oracle original |

**The model.** Every end statement with an adversary is in the random-permutation model (`lean_da`'s code binding assumes the argument's knowledge soundness in it; `decode_binds` and `GuestKnowledge` are about the deployed Keccak-256, with no oracle): one uniformly random permutation `π` of the 1600-bit Keccak state, which the adversary queries forward (`π`) and inverse (`π⁻¹`), Keccak-256 the sponge over `π` and Keccak-f[1600] `π` itself. That the deployed Keccak-f[1600] behaves as a random permutation is the assumption. The guest's statements about its own execution use the deployed Keccak-256 (inside the circuit it is computed, not queried): there the assumption is that no one finds a collision of the deployed Keccak-256 (`aggregate_sound_outer`'s collision clause, `decode_binds`). The `formal/` folder of leanVM's checkout (`.leanvm/`) holds leanVM's own, older copies of `lean_xmss` and `lean_sphincs`, with random-oracle theorems and bounds; the statements here supersede them. **How the proofs reach it** (proof, not statement): each project first proves its theorems with Keccak-256 (and, in `lean_vm` and `lean_da`, Keccak-f[1600]) independent random oracles, then `common`'s indifferentiability of the Keccak-256 sponge from a random oracle moves them to the random-permutation model, at `q² / 2^509` for `q` permutation calls, or `q² / 2^508` with direct permutation calls in a duplex (`Common.keccak256_transfer`, `keccak256_transfer2`).

Each is its own Lake project on the toolchain in [`lean-toolchain`](lean-toolchain), with the same pinned dependencies. The dependencies go one way: `Statement` (Mathlib, VCVio, CompPoly) ← `common` ← `lean_xmss`, `lean_sphincs`, `lean_da` ← `lean_vm`, each by path, and every project requires `Statement` directly.

## Building and checking

`lake build` here runs [`check-all.sh`](check-all.sh): for each project, in turn and in its own directory, what [`.github/workflows/lean.yml`](.github/workflows/lean.yml) runs: no proof escapes, the statement's imports, the build, no deprecated API, the axiom footprints and `lake test`, then the checks against leanVM below, which need `cargo`. `./check-all.sh lean_vm` (or any of `lean_xmss lean_sphincs lean_da lean_vm leanvm`) runs some. A cold build is several CPU-hours. [`lake-build.py`](lake-build.py) builds the statement and `lean_vm` (`python3 -I lake-build.py lean_vm LeanVM LeanVMTests`, or any project's targets): one `lake build`, its modules admitted by memory with the cores busy.

## Against leanVM

[`leanvm-rev`](leanvm-rev) is the leanVM commit whose verifier, guest and prover `lean_vm` is about. [`leanvm-tree.sh`](leanvm-tree.sh) checks it out into `.leanvm/`, with its `formal/lean_vm` a link to `lean_vm/`. There the Rust verifier is fuzzed against the Lean one, and `lean_vm/scripts/guest-export` writes the aggregation guest's data (its bytecode into `Statement/Data/`) and the node vectors from leanVM's sources (at this pin leanVM has no tests that write Lean data); CI runs both.

leanVM's own `formal/` goes on changing. Following it is deliberate: bump `leanvm-rev`, carry over the matching `formal/` changes, and let the checks above say what is stale. The generated data's headers and some prose still name leanVM's paths (`formal/lean_vm/…`, `crates/…`); those are citations into the leanVM tree.
