# leanerVM

Lean 4 proofs about [leanVM](https://github.com/leanEthereum/leanVM): its verifier, and the signature schemes and data-availability scheme its aggregation guest checks. The four projects are leanVM's `formal/` at the commit in [`leanvm-rev`](leanvm-rev) (branch `FV`), with their history.

| Path | What it proves |
| --- | --- |
| [`lean_vm/`](lean_vm/README.md) | leanVM's verifier at `main` (`94ee12ff`, the `keccak-gkr` branch merged, and the machine halting in the final state `(pc, fp) = (g^(N-1), 1)`: Keccak-256 hashing, a Keccak-f[1600] duplex sponge for Fiat-Shamir, the `KECCAK` instruction proved by GKR over the rounds), knowledge sound with a fixed straight-line extractor (information-theoretic: its running time is not part of the statement), and complete, in the random-permutation model: Keccak-256 and Keccak-f[1600] built from one random permutation `π`, which the adversary queries forward and inverse (`LeanVM.knowledgeSoundness_holds`, `LeanVM.completeness_holds`; knowledge soundness at most `(Q + 2^14) · 2^-127` for `Q ≤ 2^120` permutation queries, `LeanVM.knowledgeSoundness_bits`). The aggregation guest is knowledge sound with its witness named, read off the execution's memory (`LeanVM.Guest.End.guest_knowledge`, `decode_binds`, and in the random-permutation model `aggregate_sound_outer`), and complete within an explicit budget linear in a node's work, each child charged by its announced stack log and rate (`LeanVM.Guest.Budget.guest_complete`), which covers every node of up to 16 children (the guest's `MAX_RECURSIONS`, at every stack log and rate a child announces) and 2048 declared claims, coverage slots and children's claims, holding no signature or blob directly, and every leaf of up to 2048 raw signatures, declared claims and coverage slots (`guest_complete_recursion`, `guest_complete_leaf`): see [`lean_vm/README.md`](lean_vm/README.md#the-guests-proof) |
| [`lean_rpm/`](lean_rpm/README.md) | the random-permutation model (a uniform permutation π with π and π⁻¹ queries), the indifferentiability of the Keccak-256 sponge from a random oracle (q²/2^509), and the transfer of random-oracle bounds to the random-permutation model, for Keccak-256 alone and with direct permutation calls in leanVM's duplex (q²/2^508) |
| [`lean_xmss/`](lean_xmss/README.md) | leanXMSS's SUF-CMA security in the random-permutation model, `Q / 2^127 + Q² / 2^509` for `Q` permutation calls (`XmssSecurity.leanXmss_rpm_security`), from its 127 bits in the random-oracle model (`XmssSecurity.leanXmss_has_127_bits_of_classical_security`, a step of the proof) |
| [`lean_sphincs/`](lean_sphincs/README.md) | leanSPHINCS's SUF-CMA security in the random-permutation model, `Q / 2^127 + Q² / 2^509` for `Q` permutation calls, at every proved lifetime (`Sphincs.Lifetimes.requestedSecurityRpm`), from its 127 bits in the random-oracle model (`Sphincs.Lifetimes.requestedSecurity`, a step of the proof) |
| [`lean_da/`](lean_da/README.md) | LeanDA's completeness, position binding and code binding: Benedikt Wagner's framework and proofs ([b-wagn/fv-pq-da](https://github.com/b-wagn/fv-pq-da), [his post](https://ethresear.ch/t/formally-verified-security-for-pq-das-leanda/25746)), ported and instantiated with LeanDA, and moved to the random-permutation model: position binding `Q² / 2^256 + Q² / 2^508` (`LeanDa.leanDa_positionBinding_rpm`) and code binding at Wagner's bound plus `Q² / 2^508 + 2 (Q + 15)² / 2^576` (`LeanDa.leanDa_codeBinding_rpm_bound`) for `Q` permutation calls |

**The model.** Every end statement with an adversary is in the random-permutation model (`lean_da`'s code binding keeps Wagner's terms over a random function table, as its README says; `decode_binds` and `GuestKnowledge` are about the deployed Keccak-256, with no oracle): one uniformly random permutation `π` of the 1600-bit Keccak state, which the adversary queries forward (`π`) and inverse (`π⁻¹`), Keccak-256 the sponge over `π` and Keccak-f[1600] `π` itself. That the deployed Keccak-f[1600] behaves as a random permutation is the assumption. **How the proofs reach it** (proof, not statement): each project first proves its theorems with Keccak-256 (and, in `lean_vm` and `lean_da`, Keccak-f[1600]) independent random oracles, then `lean_rpm`'s indifferentiability of the Keccak-256 sponge from a random oracle moves them to the random-permutation model, at `q² / 2^509` for `q` permutation calls, or `q² / 2^508` with direct permutation calls in a duplex (`LeanRpm.keccak256_transfer`, `keccak256_transfer2`).

Each is its own Lake project on the toolchain in [`lean-toolchain`](lean-toolchain); `lean_xmss`, `lean_sphincs` and `lean_da` require `lean_rpm` by path, and `lean_vm` requires those three by path, for their `Scheme` modules, and `lean_rpm`, for its statements in the random-permutation model.

## Building and checking

`lake build` here runs [`check-all.sh`](check-all.sh): for each project, in turn and in its own directory, what [`.github/workflows/lean.yml`](.github/workflows/lean.yml) runs: no proof escapes, the build, no deprecated API, the axiom footprints and `lake test`, then the checks against leanVM below, which need `cargo`. `./check-all.sh lean_vm` (or any of `lean_xmss lean_sphincs lean_da lean_vm leanvm`) runs some. A cold build is several CPU-hours.

## Against leanVM

[`leanvm-rev`](leanvm-rev) is the leanVM commit whose verifier, guest and prover `lean_vm` is about. [`leanvm-tree.sh`](leanvm-tree.sh) checks it out into `.leanvm/`, with its `formal/lean_vm` a link to `lean_vm/`. There the Rust verifier is fuzzed against the Lean one, and `lean_vm/scripts/guest-export` writes the aggregation guest's data and the node vectors from leanVM's sources (at this pin leanVM has no tests that write Lean data); CI runs both.

leanVM's own `formal/` goes on changing. Following it is deliberate: bump `leanvm-rev`, carry over the matching `formal/` changes, and let the checks above say what is stale. The generated data's headers and some prose still name leanVM's paths (`formal/lean_vm/…`, `crates/…`); those are citations into the leanVM tree.
