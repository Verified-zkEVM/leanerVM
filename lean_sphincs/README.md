# leanSPHINCS security in Lean 4

**`Sphincs.leanSphincsStronglyUnforgeable` proves that leanSPHINCS, the scheme of [`crates/signatures/src/lean_sphincs`](https://github.com/leanEthereum/leanVM/tree/5e3ade21/crates/signatures/src/lean_sphincs) specified in [`doc/lean_sphincs`](https://github.com/leanEthereum/leanVM/tree/5e3ade21/doc/lean_sphincs), at leanVM commit `5e3ade21`, is SUF-CMA secure in the random-permutation model up to `N = 1,182,000,000` signatures, with forgery probability at most `(Q + 1) · 2^-127` for `Q ≥ 1` permutation calls.** ([Security.lean](Sphincs/Security.lean); the statement is `Sphincs.LeanSphincsStronglyUnforgeable` in [`Statement/LeanSphincs.lean`](../Statement/LeanSphincs.lean).) The hash `H` of `Th(P, A, M) = Truncate_16(H(P ‖ A ‖ M))` is Keccak-256, the sponge over a uniformly random permutation `π` of the Keccak state, and the adversary queries `π` and `π⁻¹` besides the signing oracle. `Q` counts every permutation call on every path of the game, key generation, the honest signer and the final verification included (a hash of `n` bytes costs `⌊n / 136⌋ + 1`). [Sphincs/Axioms.lean](Sphincs/Axioms.lean) and [FORS/Axioms.lean](FORS/Axioms.lean) pin the axioms to `propext`, `Classical.choice` and `Quot.sound` with `#guard_msgs`; there is no `sorry` and no `native_decide`, and every numeric certificate is checked by the kernel.

## The route

1. **The random-oracle theorem** (a step, not an end statement): `FORS.h26_layered`, 127 bits of classical SUF-CMA security in the random-oracle model for `q` hash calls, `q / 2^127`, at the configuration `.layered 26 3 8 24 10 1182000000` (three layers of 10 + 8 + 8 from the top, FORS of 24 trees of height 10). The library [`FORS`](FORS) is leanVM's `formal/lean_sphincs` at `5e3ade21` (FIPS 205's addresses, `SK.seed` as the key, one `PRF` call per secret, `PRF_msg` on the framed message `M' = 0x00 ‖ 11 ‖ leanSPHINCS ‖ M`, `H_msg` on the 32-byte message `M` unframed, read as FIPS 205's Algorithm 19), ported from upstream's toolchain to this repository's pins (Lean v4.34.1, Mathlib v4.34.1, VCVio `afa6593f`): names, namespaces and statements are upstream's, the proofs repaired for the toolchain (VCVio's measure-valued `evalDist`, the `Pr{…}[…]` notation, renamed lemmas, deprecations removed so that warnings are errors, file-level heartbeat raises removed). Its game's key generation and signer are upstream's model (`FORS.Seeded.keygen`, `FORS.Seeded.sign`: a landing call before the digest, sibling subtrees, the verifier's recomputation of each layer's root). Upstream's [README](https://github.com/leanEthereum/leanVM/tree/5e3ade21/formal/lean_sphincs) describes the proof.
2. **The crate's key generation and signer**: the crate's (`keygen`, `sign_with`: the key expanded again, the whole top tree rebuilt, every FORS tree and every lower layer's tree built once, level by level) is not the model's call for call, but has the same values with at least its hash calls. Its copy in the model's hash monad, function for function the statement's, is `FORS.Crate.keygen` / `FORS.Crate.sign` ([FORS/Crate.lean](FORS/Crate.lean)); on every answer function of the hash it gives the model's public key and signatures with at least the model's calls ([FORS/CrateStatic.lean](FORS/CrateStatic.lean): `eval_keygen`, `eval_sign`, `hashCalls_keygen`, `hashCalls_sign`), and both query only inputs of at most 2084 bytes ([Queries.lean](Sphincs/Queries.lean)). `Common.SufCma.StaticSwap.romBound` (`common/Common/StaticSwap.lean`: the finite honest part of the random oracle sampled in advance, then the same success and, path by path, at most the swapped scheme's hash calls) moves the model's bound to the crate's copy at its own count (`Sphincs.Model.crateScheme_romBound`, [ModelRpm.lean](Sphincs/ModelRpm.lean)).
3. **The random-permutation model**: `Sphincs.Model.crateScheme_stronglyUnforgeable` ([ModelRpm.lean](Sphincs/ModelRpm.lean)). The model's game is the generic SUF-CMA game of `common` (`experiment_eq`), and `Common.SufCma.rpm_bound` (the indifferentiability of the Keccak-256 sponge from a random oracle, `Q² / 2^509`) gives `Q / 2^127 + Q² / 2^509 ≤ (Q + 1) · 2^-127` for `Q ≤ 2^128`.
4. **The statement's scheme is the crate's copy**: [Model.lean](Sphincs/Model.lean) proves that the model's verifier, its hash queries answered by Keccak-256 over `π`, is the statement's (`simulateQ_verify`), through the maps of the keys and signatures: the model numbers the layers from the top, the statement from the bottom as the crate does (`toLayer`); a layer's path has the model's length or the statement's, equal at each layer (`signatureEquiv`); every hash input is the same bytes (`fieldBytes_hashDomainFields`: the model's 96-bit tree word is the statement's zero word and 64-bit tree); the model packs the digest's index and FORS leaves into one bit vector, the statement reads them off its 34 bytes, and both are FIPS 205's Algorithm 19 on the calls' bytes (`digestIndex_eq`, `digestLeaves_eq`). [CrateSim.lean](Sphincs/CrateSim.lean) proves the same of the crate's copy's key generation and signer (`simulateQ_crateKeygen`, `simulateQ_crateSign`). [Transport.lean](Sphincs/Transport.lean) proves that such a scheme has the crate's copy's game, adversary by adversary, and [Bridge.lean](Sphincs/Bridge.lean) moves the bound across (`stronglyUnforgeable_of_model`).

## The model and the Rust code

`Statement/LeanSphincs.lean` transcribes the crate (citations at `5e3ade21`): its key generation and signer are the crate's, hash call for hash call, so the budget counts the crate's hash calls, and the secret key is the crate's, the seed `SK.seed`. It is checked against the crate by reading both sides and by running the compiled statement on the crate's known answers (`lake exe signature-kat`, [cli/SignatureKat.lean](cli/SignatureKat.lean)): the EthLib vectors (`crates/signatures/tests/signatures/ethlib`: key generation, signing and verification of leanXMSS, the rejected inputs of the wrong length included; leanVM `5e3ade21` has none for leanSPHINCS) and leanSPHINCS's known answer (`known_answer.hex`: the public key, the signature and its verification). At `5e3ade21` everything matches: leanSPHINCS's known answer (the public key, the signature and its verification) and leanXMSS's EthLib vectors (key generation 4/4, signing 6/6, verification 20/20, no mismatch). It is not a mechanized refinement of the Rust.

## Build

```sh
cd lean_sphincs
lake exe cache get
python3 -I ../lake-build.py . --mem 28
# the crates' known answers, from a leanVM checkout at the cited commit
lake build signature-kat
.lake/build/bin/signature-kat ../.leanvm/crates/signatures/tests/signatures/ethlib \
  ../.leanvm/crates/signatures/src/lean_sphincs/known_answer.hex
```
