# leanSPHINCS security in Lean 4

**`Sphincs.leanSphincsStronglyUnforgeable` proves that leanSPHINCS, the scheme of [`crates/signatures/src/lean_sphincs`](https://github.com/leanEthereum/leanVM/tree/b7a8d0cb/crates/signatures/src/lean_sphincs) specified in [`doc/lean_sphincs`](https://github.com/leanEthereum/leanVM/tree/b7a8d0cb/doc/lean_sphincs), at leanVM commit `b7a8d0cb`, is SUF-CMA secure in the random-permutation model up to `N = 1,182,000,000` signatures, with forgery probability at most `(Q + 1) · 2^-127` for `Q ≥ 1` permutation calls.** ([Security.lean](Sphincs/Security.lean); the statement is `Sphincs.LeanSphincsStronglyUnforgeable` in [`Statement/LeanSphincs.lean`](../Statement/LeanSphincs.lean).) The hash `H` of `Th(P, A, M) = Truncate_16(H(P ‖ A ‖ M))` is Keccak-256, the sponge over a uniformly random permutation `π` of the Keccak state, and the adversary queries `π` and `π⁻¹` besides the signing oracle. `Q` counts every permutation call on every path of the game, key generation, the honest signer and the final verification included (a hash of `n` bytes costs `⌊n / 136⌋ + 1`). [Sphincs/Axioms.lean](Sphincs/Axioms.lean) and [FORS/Axioms.lean](FORS/Axioms.lean) pin the axioms to `propext`, `Classical.choice` and `Quot.sound` with `#guard_msgs`; there is no `sorry` and no `native_decide`, and every numeric certificate is checked by the kernel.

## The route

1. **The random-oracle theorem** (a step, not an end statement): `FORS.h26_layered`, 127 bits of classical SUF-CMA security in the random-oracle model for `q` hash calls, `q / 2^127`, at the configuration `.layered 26 3 8 24 10 1182000000` (three layers of 10 + 8 + 8 from the top, FORS of 24 trees of height 10). The library [`FORS`](FORS) is leanVM's `formal/lean_sphincs` at `542b0353`, ported from Lean v4.31.0 and VCVio `cbd4144` to this repository's pins (Lean v4.34.1, Mathlib v4.34.1, VCVio `afa6593f`), with one change of substance: **the game's signer `FORS.Seeded.sign` is the crate's** (`sign_with`, call for call: the randomizer, the digest's two calls, each FORS tree built once for its key and its opening, then the layers from the bottom up, each a WOTS+C signature followed by its tree built once). Upstream's signer, written for every shape (`FORS.Seeded.signModel`), rebuilds trees, signs the layers from the top down and makes a landing call before the digest; it is kept as the reference the crate's signer is proved to compute (`FORS.Security.GraphView.eval_sign_eq_finishSign`, `GraphView/CrateSigner.lean`, for a full or layered key, `subtreeHeight = totalHeight`). The proof's graph view charges the honest signer's work as ticks of its exact hash calls (`GraphView/CountedGame.lean`); it now runs the layers from the bottom up (`Concrete.sequenceLayersUp`) with the crate's charges: the FORS instance built once (less the scan's landing call, which the view keeps as a query), and per layer the counter search and, on success, the chain values and the whole tree (`signCostDet_correct`, `Reduction/CostProgram.lean`). The potential arguments are generic in these charges and in the order of the layers; the final assembly theorem takes `subtreeHeight = totalHeight` (`ForsPotential.det_bitsFH`). Names, namespaces and the other statements are upstream's; the proofs are repaired for the toolchain (VCVio's measure-valued `evalDist`, the `Pr{…}[…]` notation, renamed lemmas, deprecations removed so that warnings are errors, file-level heartbeat raises removed), and one helper file of our earlier port, [`FORS/Base/Probability.lean`](FORS/Base/Probability.lean). Upstream's [README](https://github.com/leanEthereum/leanVM/tree/542b0353/formal/lean_sphincs) describes the proof.
2. **The crate's secret key, the seed `S0`**: the statement's signer derives the scheme seed `S = H(leanSPHINCS ‖ S0)` and the public parameter again at each signature, as the crate does; upstream's game hands the signer `S` and `P`. In the random-oracle game these derivations hit the cache that key generation filled, so the game with the seed as the key is the game with `(S, P)` in distribution, and at least as costly on every path: a random-oracle bound passes to it at its own count (`Common.SufCma.SeedKeyed.romBound`, `common/Common/SeedKey.lean`; `Sphincs.Model.seedKeyed`).
3. **The random-permutation model**: `Sphincs.Model.modelScheme_stronglyUnforgeable` ([ModelRpm.lean](Sphincs/ModelRpm.lean)). The model's game is the generic SUF-CMA game of `common` (`experiment_eq`), and `Common.SufCma.rpm_bound` (the indifferentiability of the Keccak-256 sponge from a random oracle, `Q² / 2^509`) gives `Q / 2^127 + Q² / 2^509 ≤ (Q + 1) · 2^-127` for `Q ≤ 2^128`.
4. **The statement's scheme is the model's**: [Model.lean](Sphincs/Model.lean) and [ModelSigner.lean](Sphincs/ModelSigner.lean) prove that each of the model's algorithms, its hash queries answered by Keccak-256 over `π`, is the statement's (`simulateQ_verify`, `simulateQ_keygen`, `simulateQ_sign`), through the maps of the keys and signatures: the model numbers the layers from the top, the statement from the bottom as the crate does (`toLayer`); a layer's path has the model's length or the statement's, equal at each layer (`signatureEquiv`); every hash input is the same bytes (`fieldBytes_hashDomainFields`). [Transport.lean](Sphincs/Transport.lean) proves that such a scheme has the model's game, adversary by adversary, and [Bridge.lean](Sphincs/Bridge.lean) moves the bound across (`stronglyUnforgeable_of_model`).

## The model and the Rust code

`Statement/LeanSphincs.lean` transcribes the crate (citations at `b7a8d0cb`): its key generation and signer are the crate's, call for call, so the budget counts the crate's hash calls, and the secret key is the crate's, the seed `S0`. It was checked against the crate by reading both sides and by running the compiled statement on the crate's known answers (`lake exe signature-kat`, [cli/SignatureKat.lean](cli/SignatureKat.lean)): the EthLib vectors of `542b0353` (`crates/signatures/tests/signatures/ethlib`: leanSPHINCS's key generation 4/4, signing 5/5 and verification 24/24; leanXMSS's key generation 4/4, signing 6/6 and verification 20/20; the rejected inputs of the wrong length included) and leanSPHINCS's known answer (`known_answer.hex`: the public key, the signature and its verification). It is not a mechanized refinement of the Rust.

## Build

```sh
cd lean_sphincs
lake exe cache get
python3 -I ../lake-build.py . --mem 28
# the crates' known answers, from a leanVM checkout at the cited commit
lake build signature-kat
.lake/build/bin/signature-kat ../.leanvm/crates/signatures/tests/signatures/ethlib \
  ../.leanvm/crates/signatures/src/lean_sphincs/known_answer.hex
```
