## Two requests

1. **`Caps` should require power-of-two heights and bytecode length.** The M3 model has columns of height `2^κ`, the verifier accepts only the announced log-heights `τ_j` and a bytecode length `2^{k_bc}`, and `constraintCompleteness` already pads every table with fill blocks. If `Caps` includes `∀ j, (tables[j]).length = 2^(τ j)` (and the BLAKE2S floor `τ_5 ≥ 3`, already there), then `SatisfiedBy` is exactly the relation the proof system proves and extracts, and the two roadmaps state one relation. Otherwise the protocol roadmap's Layer 3 adds the conjunct locally and there are two relations to keep aligned.

2. **Each channel should carry its bus data.** The bus fingerprints 16-slot `K`-tuples whose coordinate 0 is the domain separator (`g^0` state, `g^1` memory, `g^2` bytecode) and whose remaining coordinates follow the specification's tuple order, zero-padded. Layer 5's six typed channels (`StatePull` … `BytecodePush`) determine this data, but only by convention. Making it explicit — a function from the channel to its separator, and from the typed message to its coordinate vector (the `sep`/`dir` arguments of `Component.toM3` in the protocol roadmap's Layer 2) — lets the proof system read the bus off leanISA's channels instead of transcribing the tuples a second time. The message types' `ProvableStruct` element order is the natural candidate if it matches `tables.rs` coordinate order; the roadmap's Layer 2 test checks it.

Neither request changes a theorem of the leanISA roadmap; the first narrows `Caps` (which completeness already meets) and the second adds data to Layer 5.
