               How to prove more false statements:
           Fiat–Shamir limitations on (generated) R1CS

                                      Giacomo Fenzi

                                           Abstract
     The Fiat–Shamir (FS) transformation is a technique that converts interactive protocols into
non-interactive ones. FS is secure in idealized models such as the random oracle model (ROM)
(if the interactive protocol satisfies a condition known as state-restoration soundness).
     It is known that there are protocols whose FS transformation is secure in the ROM, yet
insecure when instantiated with any concrete hash function. Historically, these protocols were
contrived (as in, they were designed so their FS transformation would be unsound). Khovra-
tovich, Rothblum and Soukhanov (CRYPTO 2025) showed that a class of natural (and practi-
cally deployed) protocols based on a protocol of Goldwasser, Kalai and Rothblum (JACM 2015)
was also unsound when compiled with FS and any concrete hash function.
     We extend the attack to a different class of protocols: those whose instances are generated
by running a program.
     This setting covers concrete trends in modern proof systems, in which the computation
to be proven is described by a program (often adversarialy generated) which is then either
compiled or autonomously converted into an instance of target relation such as rank-1 constraint
satisfaction (R1CS). We show that, when the conversion process is “expressive enough”, an
adversary controlling the program code can break soundness of the non-interactive proof system.
     The attacks generalize to a wide class of protocols: any protocol in which a cheating prover
can prepare an accepting transcript before the statement is bound. We show that variants of
the Spartan (CRYPTO 2020) and Aurora (EUROCRYPT 2019) proof systems for R1CS fall in
this class.
     Complementing the attacks, we formalize a mitigation: deriving the Fiat–Shamir challenges
from the generated statement, rather than from the program that generates it, provably reduces
the soundness of the compiled protocol to that of the underlying protocol for the non-generated
relation.

Keywords: succinct arguments; Fiat–Shamir; diagonalization

1     Introduction
Succinct non-interactive arguments (SNARGs) [Mic00] have emerged as a fundamental crypto-
graphic primitive. They allow a prover to certify the correct execution of a computation with a
proof that can be exponentially smaller, and substantially faster to verify, than the computation
itself. SNARGs now support applications ranging from distributed computation to digital identity
systems.
Fiat–Shamir transformation. A common route to concretely efficient SNARGs, including the
families studied here, is to apply the celebrated Fiat–Shamir transformation [FS86] to a public-
coin interactive proof (or argument). The transformation removes interaction by replacing each
verifier message with a hash of the transcript so far. Intuitively, the transformation is sound
since a prover should be unable to predict the verifier message without hashing the preceding
transcript. The intuition can be formalized in the random oracle model (ROM) [BR93], where
the hash function is modeled as an ideal random function: on each previously unqueried input, it
returns an independent, uniformly distributed string in {0, 1}λ . Under suitable conditions on the
interactive protocol, Fiat–Shamir yields a secure SNARG in the ROM [PS96; BCS16; CCHLRR18].
    The ROM, however, is an idealized model: protocols that are secure in the ROM might not be
secure when the random oracle is instantiated with a concrete hash function.
    We seek to understand when Fiat–Shamir remains secure after replacing the random oracle
with a concrete hash function.
Limitations of Fiat–Shamir. Prior work constructed protocols whose Fiat–Shamir compilations
are secure in the ROM but insecure for every concrete choice of hash function [Bar01; GK03;
CGH04]. More precisely, these protocols are adaptively unsound: once a concrete hash function
is chosen, a malicious prover can prove a false statement (both the statement and the proof may
depend on the hash choice). The protocols refuted the conjecture that any protocol that is secure in
the ROM after Fiat–Shamir is secure when the ROM is instantiated with a sufficiently good hash
function. However, the counterexample protocols (and subsequent work [BBHMR19; BHK26])
were specifically designed to refute the conjecture and thus were relatively contrived, which led to
a revised informal conjecture that any “natural” protocol that after compilation is sound in the
ROM remains sound in the plain model for an appropriate hash function.
    Khovratovich, Rothblum, and Soukhanov [KRS25] refuted this revised conjecture, showing
that a natural protocol combining the GKR protocol [GKR15] with a polynomial commitment
scheme [KZG10] was insecure after Fiat–Shamir compilation with any concrete hash function.
    The counterexample exploited the (desirable) property of GKR that it need not commit to
the internal wires of the computation being proved. A malicious prover can exploit this flexibility
to construct a circuit that internally computes its own first Fiat–Shamir challenge and then uses
the knowledge of the challenge to violate soundness. The attack affected concretely deployed
systems [Pol24] and prompted work on mitigations [AY25].
    Since the result of [KRS25] relied crucially on the structure of the GKR protocol (namely on
the property that it does not commit to the internal wires), one might wonder the following:

    To what extent do [KRS25]-style counterexamples to Fiat–Shamir rely on the structure of the
                                     protocol being attacked?

1.1      Our results
In this work, we continue the study of counterexamples to the Fiat–Shamir heuristic. We write
FSh (IP) for the compilation of an interactive protocol IP with a hash function h. From prior work,
we know that as long as IP is state-restoration sound (resp. state-restoration knowledge sound) and
h is a random oracle then FSh (IP) is an adaptively sound (resp. knowledge-sound) non-interactive
argument in the ROM (see, e.g., [CY24]).

Theorem 1 (Informal). There exists a relation R such that FSh (IP) is not adaptively sound for
any “natural” IP for R and any sufficiently efficient hash function h.

   In Section 1.2 we elaborate on the details of Theorem 1 (including the definition of naturality,
and the relation between the complexity of h and the naturality of IP).
Concrete instantiation. We define generated R1CS RR1CS [c], which is a variant of the rank-1-
constraint satisfaction (R1CS) relation [GGPR13] that fulfils the promise of Theorem 1: FSh (IP)
is not adaptively sound for any IP for RR1CS [c] that satisfies the naturality condition and concrete
hash function h.
    We show that the compilation of two popular interactive oracle proofs (IOPs) [BCS16; RRR16]
for R1CS (namely the univariate IOP of [BCRSVW19] and the multilinear IOP of [Set20]) yields
protocols that are natural in the sense of Theorem 1. Letting BCSh (IOP) denote the compilation
of IOP using a hash function h, since these IOPs are round-by-round knowledge sound, we obtain
the following corollary.

Corollary 1 (Informal). There exists an IOP for generated R1CS RR1CS [c] such that:

• if h is a random oracle, BCSh (IOP) is adaptively knowledge sound in the ROM.

• for any concretely efficient1 hash function h, BCSh (IOP) is not adaptively sound.

As in prior work, our techniques to attack the Fiat–Shamir heuristic rely on diagonalization. Our
aim will be for the adversary to construct an instance that “knows its own Fiat–Shamir challenge”,
and use this to attack soundness. We first recall the adaptive Fiat–Shamir transformation.

Definition 1 (Informal). Let c > 1 be an arbitrary constant3 . The c-generated CSAT relation
is the relation consisting of x = (1T , 1n , 1m , s), w = x ∈ {0, 1}n such that:
• When s is interpreted as a deterministic program, it runs in at most T c steps and generates a

• φ(x) = 1.
   Generated relations have a peculiar feature: one can diagonalize the instance using a version of
Kleene’s second recursion theorem [Kle52].
Claim 1 (Informal). In a standard programming model, for every program F there is an efficiently
computable program s⋆ such that executing s⋆ yields F (s⋆ ). Further, |s⋆ | = O(|F |) and constructing
it takes time poly(|F |). If F (s⋆ ) can be computed in T steps, then executing s⋆ takes (T + |F |) ·
poly(|F |, log T ) steps.
   Concretely, given an arbitrary program F , an instance x of the generated relation can contain a
program s⋆ that computes F (s⋆ ): s⋆ computes an arbitrary function of its own code. In our attack,
one can let F be the program that computes a prover message m1 and the Fiat–Shamir hash
ρ1 = h(1, x, m1 ). In the context of c-generated CSAT, one can then produce a circuit that contains
the verifier randomness ρ1 that the verifier of the Fiat–Shamir transformation would recompute.
   Many PCPs, IOPs and interactive arguments for c-generated CSAT have the following two
properties.
Definition 2 (Informal). An interactive k-round verifier V for c-generated CSAT is semantic if
its decision depends on the instance only through the generated statement: there is a verifier V
such that V(x, ·) = V(φ, ·) whenever the program in x generates φ.

Remark 1. The “sufficiently efficient” in Theorem 2 refers to the relation between the budget c in
the c-generated CSAT relation and the exponent d in the running time of s⋆T . This latter exponent
depends on the complexity of the hash function h, the efficiency of the malicious algorithms in the
diagonalization and the complexity of constructing the fixed point. The attack succeeds as long as
c > d.

Remark 2. Definition 2 captures a wide class of protocols for generated relations. We are not
aware of natural proof systems that avoid it, other than trivial ones (such as the ones where the
prover sends the NP-witness and the verifier checks membership in the relation) or ones in which
the generation of the instance from the program is also itself proven (instead of computed).

Concrete implications. In Sections 6 and 7 we show that two round-by-round knowledge sound
IOP families for the generated R1CS relation are semantic and fooled by delayed statement choice
in the sense of Definition 2. The IOPs are (trivial) adaptations of existing IOPs for R1CS, where
additionally the prover and verifier run the generating program s to derive the R1CS matrices.
Theorem 2 straightforwardly adapts, which proves Theorem 1: there exist IOPs for generated
R1CS that are insecure when compiled via the BCS transformation with any sufficiently efficient
hash function h. While generated R1CS may seem like a contrived relation, it is somewhat close
to practically relevant designs of proof systems for R1CS. In modern proof systems, the user wants


                                                      5
to prove a computation, say s(w) = 0, in some computation model. The code s of the computa-
tion being proven is then interpreted or compiled into corresponding R1CS matrices. When s is
untrusted, it is hard to guarantee that the compilation process cannot be (possibly undetectably)
influenced to generate instances that satisfy the preconditions for our attacks. In that case, if the
Fiat–Shamir hash contains only s (or a commitment to s in the preprocessing case) the protocol
may be vulnerable. Luckily, there are mitigations that can be taken.

• If the R1CS matrices are used as the statement identifier in Equation 1, then the attacks that
  we describe do not apply. In fact, hashing the generated statement provably reduces adaptive
  soundness to that of the underlying non-generated protocol (Theorem 5.5).

• The attack also requires the adversary to specify a chosen computation s to be proven. We
  recommend caution and careful audits in any setting in which such computations are fully or
  partially under the control of third parties (e.g. when compiling user code, automatic precom-
  piles, AI-generated circuits, and similar).

• [AY25] describes a variant of the Fiat–Shamir called Extended Fiat–Shamir (XFS), designed
  to prevent the diagonalization that this paper and [KRS25] employ. XFS prevents the attacks
  in this paper, at the cost of a more expensive verifier. To our knowledge, the security proofs
  in [AY25] do not give provable guarantees that XFS prevents variants of the attacks in the paper.

   While our concrete IOP attacks target R1CS, the generated-relation construction of Section 4
applies to any relation: for every relation R and every budget exponent c, the c-generated variant
R[c] has a self-referential semantic scheme. We thus believe our attacks apply to other relations
and designs, such as proof systems for virtual machines, as long as the relation is (partially or fully)
generated. Other transformations such as [Fis05] are similarly vulnerable.
Theoretical implications. Our results give limitations on showing security guarantees for in-
teractive protocols compiled with Fiat–Shamir in the plain model. We showed that any natural
protocol (in the sense of Definition 2 and definition 3.3) for generated relations (Definition 3.2)
is insecure when compiled via Fiat–Shamir instantiated with a sufficiently efficient hash function
h. Positive results on the vanilla Fiat–Shamir transformation must therefore circumvent at least
one of these caveats. For a protocol to be secure after Fiat–Shamir in the plain model: either
the protocol must not be natural (which seems to require deviating from common techniques in
building interactive proof systems), or the relation must not be generated (which rules out generic
statements that handle every NP-relation) or the hash function must be inefficient (which is, gener-
ally, undesirable). We believe understanding the limitations of Fiat–Shamir and Fiat–Shamir-like
transformations to be a central stepping stone for proving future positive results.

1.3   Related work
Closely related to our work is [KRS25, Section 4]. A strawman mitigation to the diagonalization
attacks that they present would be inspecting the GKR circuit proven to ensure that it does
not contain an implementation of the FS hash function or the commitment scheme employed.
In [KRS25, Section 4], the authors show that this mitigation is insufficient, by using universal
computation and quines (which also appear in our techniques). [KRS25, Section 4.1] chooses the
GKR circuit to interpret the witness as a program, and then chooses the witness to be a self-
referential program. The attack is impractical as the malicious prover has to prove a universal


                                                   6
machine execution through GKR. [KRS25, Section 4.2] extends this attack by using commitment
decomposition to (for specific commitments) to avoid universal machine simulation.
   Our work uses related self-reference techniques, but places the self-referential program in the
generation of the statement, rather than in the GKR circuit. This has the advantage that it imposes
minimal requirements on the proof system used: our attack extends to non-GKR based protocol
such as variants of Spartan and Aurora over generated R1CS.

2.4   The Fiat–Shamir transformation
A public-coin interactive protocol IP = (P, V) for a relation R works as follows. The prover
receives (x, w) ∈ R and the verifier receives x. In each round i ∈ [k], P sends a message mi and V
replies with a uniformly random ρi ∈ {0, 1}ri . After k rounds, V reads the transcript and accepts
or rejects. This is the special case of Section 2.2 in which there is no implicit instance and the
verifier reads every prover message in full; Definitions 2.5, 2.7 and 2.8 apply verbatim.
    The Fiat–Shamir transformation compiles such a protocol into a non-interactive argument by
deriving each verifier message from a hash of the transcript so far [FS86].

3     Diagonalization for programmable protocols
This section gives a general form of the diagonalization attack. We first define semantic schemes:
relations whose membership is determined by a semantic value that is separate from the instance
itself. Then, we define diagonalizable protocols, which we show to be susceptible to the techniques
in this work.

3.1   Semantic schemes
A semantic scheme gives every instance x a possible “meaning” σ, where that meaning contains
exactly the semantic information needed to decide whether x is in the relation.

Definition 3.1. Let R be a relation over explicit instances x ∈ X and witnesses w. A semantic
scheme for R is a triple S = (Σ, ⊩, R), where Σ is a set of semantic values, ⊩ ⊆ X × Σ is a
realization relation and R is a relation, such that x ⊩ σ implies, for every w,

                                 (x, w) ∈ R    ⇐⇒      (x, σ, w) ∈ R .

Write L(R) = {(x, σ) : ∃w, (x, σ, w) ∈ R}. If x ⊩ σ, then

                                 x ∈ L(R)     ⇐⇒      (x, σ) ∈ L(R) .

    While the definition of semantic schemes might seem vacuous (every relation has a semantic
scheme, namely the one where R = R and ⊩ is equality), this separation between instance and the
value of the relation allows us to define schemes that are self-referential: the semantic value σ can
depend (in an arbitrary way) on the instance x.

Definition 3.2. Let S = (Σ, ⊩, R) be a semantic scheme for R and F a set of efficiently computable
functions X → Σ. Then S is self-referential for F if there is an algorithm Fix that, given the
description of any F ∈ F , runs in time poly(|F |) and outputs an instance x⋆ := Fix(F ) ∈ X
satisfying
                                          x⋆ ⊩ F (x⋆ ) .

    Self-referential schemes will be crucial for our attacks. Clearly, the trivial semantic scheme is
self-referential for the function class F containing the identity function, but we will require a more
expressive function class (in particular, F that can compute the Fiat–Shamir hash of x).

3.2   Programmability
We define the properties that (fixing a semantic scheme) make an interactive protocol susceptible
to the results in this paper: programmability.
    In a nutshell: a programmable prover sends its first i messages, then uses the verifier challenge
prefix to choose a semantic value and (only then) completes the transcript. On every instance that
realizes the chosen semantic value, the instance must be false and the verifier must accept (thus,
breaking soundness).

    For knowledge soundness, apply the base extractor to the induced adversary on (val(x), π). By
(6), every witness it outputs is also a witness for x. Thus the knowledge error does not increase.
In both reductions the only additional cost is one evaluation of val.

6.1    Preliminaries

43       return b"".join(parts)

46   def statement_id():
47       return hash_bytes(b"generated-r1cs", b"1" * CLOCK, SOURCE.encode("utf-8"))

50   def generate():
51       commitment = merkle_root(rs_encode([1, 0]))
52       digest = hash_bytes(b"fs/zerocheck", statement_id(), commitment)
53       r1 = int.from_bytes(digest, "big") % FIELD
54       zero = [[0] * COLUMNS for _ in range(ROWS)]
55       c_matrix = [[r1, 0], [(r1 - 1) % FIELD, 0]]
56       return r1, (zero, zero, c_matrix)
