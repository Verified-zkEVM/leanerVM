# LeanDA security in Lean 4

**Credit: the security framework and its proofs are Benedikt Wagner's**, from [b-wagn/fv-pq-da](https://github.com/b-wagn/fv-pq-da) at `4475179c`, explained in his post [Formally verified security for PQ-DAS (LeanDA)](https://ethresear.ch/t/formally-verified-security-for-pq-das-leanda/25746).

**[LeanDa.lean](LeanDa.lean) proves that LeanDA, the erasure code commitment of [`crates/lean_da`](https://github.com/leanEthereum/leanVM/tree/4af2cdddd7cd41b9df2cc7e123e314a91b0b4462/crates/lean_da) specified in `doc/leanvm` §sec:leanda, is complete, position binding and code binding, for every number of rows, assuming a perfectly complete and knowledge-sound argument for its relation, all three in the random-permutation model (`leanDa_perfectlyComplete_rpm`, `leanDa_positionBinding_rpm`, `leanDa_codeBinding_rpm_bound`, [below](#the-random-permutation-model)).** The proofs of the generic construction are Benedikt Wagner's, ported here as the library `PqDas`; this project instantiates them with LeanDA, proves the building blocks they assume, and moves them to the random-permutation model. His theorems, for any hash function `H` and with the membership challenges a random oracle ([Wagner's theorems](#wagners-theorems-the-step-before-the-random-permutation-model)), are the step of the proof before that model. The root module pins the axioms of every front-page theorem to `propext`, `Classical.choice` and `Quot.sound` with `#guard_msgs`. There is no `sorry` and no `native_decide`.

## The random-permutation model

[LeanDa/RpmArg.lean](LeanDa/RpmArg.lean), [LeanDa/RpmSecurity.lean](LeanDa/RpmSecurity.lean) and [LeanDa/RpmScheme.lean](LeanDa/RpmScheme.lean) idealize Keccak-f[1600] as a uniformly random permutation `π` (`common`): `H` is Keccak-256, the sponge over `π`, and the challenges are the deployed duplex over `π` (`membershipChallengesM`, which over pure functions is `membershipChallenges`: `membershipChallengesM_id`), its state the statement's Keccak state of 25 lanes, each lane read as an element of `K` with its bits. The adversary queries `π` and `π⁻¹` alone (`Common.KSpec`, on lane states) and hashes with Keccak-256 over `π` (`Common.keccakK`), and so do the argument's prover and verifier (`NarkRpm`) and LeanDA's verifier, which verifies the argument's proof for the root once and hashes each opening's climb with Keccak-256 (`verifyCellM`, which over a pure function is `verifyCell`); the relation of the argument draws the root's challenges by the duplex over `π` (`relationM`), and its knowledge-soundness game hands the adversary's transcript to the extractor (`ksGame`, `loggedK`). The proofs give Keccak-256 an oracle of its own over the same `π` ([LeanDa/HashOracle.lean](LeanDa/HashOracle.lean): `NarkRpmH`, `ksGameH`, …, `Common.KSpecH`) and carry the end theorems back to the statement's games, each the game with the hash oracle with every hash call expanded into its permutation calls, with the same distribution and the same calls ([LeanDa/PiOnly.lean](LeanDa/PiOnly.lean), `Common.PiOnly`; the knowledge-soundness hypothesis is needed only for the code-binding adversary's own game, `leanDa_codeBinding_rpm_bound_at`). They read each game on the permutation's 200 bytes, little endian (`Common.relabel`, `common`'s `Common/Lanes.lean`: the same distribution and cost; the adversary's queries read on bytes, `relabelAdv`), and take it in the two-oracle form of `common` (`Common.rpmGame2`): the argument's verification runs right after the adversary, so it is part of the adversary there (`advV`, `advP`), and the verifier's part is the climbs, with `H` alone, and for knowledge soundness the relation's check, its duplex calls of `π` direct calls `F` (`relabel_codeBindingGame`, `relabel_posBindingGame`, `relabel_ksGame` in [LeanDa/RpmArg.lean](LeanDa/RpmArg.lean)). Every duplexing writes lanes `0 … 15` and keeps lanes `16 … 24`, so it absorbs a block whose byte `135` is that of an earlier answer, a non-final block (`duplexP_membershipChallengesR`): the duplex discipline of the two-oracle transfer `keccak256_transfer2` (`q² / 2^508`). Budgets count permutation calls on every path of the game, verifications included (`permCalls`: a query of `π` or `π⁻¹` one, so a hash of `n` bytes `⌊n / 136⌋ + 1`, the duplexing's and the argument's included; `permCallsH` with the hash oracle, `permCalls2` in the two-oracle form).

| Theorem | Statement |
| --- | --- |
| `leanDa_perfectlyComplete_rpm` | for every permutation `π`, with `H` Keccak-256 over `π` and the challenges the duplex over `π`, and every argument `ps` perfectly complete for every permutation (its prover and verifier answered by `π`, for the relation over `π`): every position of every message's honest commitment opens and verifies with probability one |
| `leanDa_positionBinding_rpm` | for every argument `ps` (any prover and verifier) and every adversary of at most `Q` permutation calls, `Pr[position binding] ≤ (Q + 1)² · 2^-256` (from `Q² / 2^256 + Q² / 2^508`, `Common.sq_add_sq_le`) |
| `leanDa_codeBinding_rpm` | for an oracle-free argument, the code-binding probabilities in the RPM and in the two-oracle ROM (`H` a random oracle, the challenges the duplex over an independent random function `F`, against the simulated adversary `advS2 A`) differ by at most `Q² / 2^508` |
| `leanDa_codeBinding_rpm_bound` | for `1 ≤ r ≤ 1024` rows, every argument `ps` (its prover and verifier querying the model's oracles) and straight-line extractor `ext` (reading the adversary's transcript): if `ps` is knowledge sound in the random-permutation model with error `(q + c) · 2^-k` for `q ≤ 2^128` calls (`ksGame`, the argument's verifier's included), then for every adversary of any number `Q` of permutation calls, `Pr[code binding] ≤ (Q + c + 2^22) · 2^-k + (Q + 2^22) · 2^-188 + (Q + 2^22)² · 2^-247`, by the straight-line argument [below](#code-binding-by-a-straight-line-argument) |

The end statements are `leanDa_perfectlyComplete_rpm`, `leanDa_positionBinding_rpm` and `leanDa_codeBinding_rpm_bound`. Wagner's forking route needs an oracle-free argument: for one, it proves, from `leanDa_codeBinding_rpm`, `leanDa_codeBinding_avg` (Wagner's bound averaged over a random `H`) and `leanDa_codeBinding_core` (its three terms bounded), the weaker bound `(Q + c + 2^22) · 2^-k + (Q + 2^20) · 2^-93 + (Q + 2^22)² · 2^-158` (`leanDa_codeBinding_fork`, a proof-side result, not an end statement); the end statement's games with the forking route's bound (`CodeBindingRpmFork`, the end statement's bound before the straight-line proof) follow from the end statement (`codeBindingRpmFork_of_codeBindingRpm`, by `straight_le_fork`).

Completeness holds for each fixed `π`, so for every outcome of the random permutation. Its proof ([LeanDa/RpmComplete.lean](LeanDa/RpmComplete.lean)) is Wagner's: the honest cells commit to the root and, a codeword, pass the membership test on every challenge (`checker_complete`), so they satisfy the relation for `π`, the argument's honest proof, answered by `π`, verifies with probability one, and the honest opening verifies (`verifyCell_openCell`). An argument complete for every permutation may also be knowledge sound in the random-permutation model, the hypothesis of code binding: its prover and verifier query the oracles.

**The argument's verification.** It runs right after the adversary in each game, so the proofs move it into the adversary's part of the two-oracle form ([LeanDa/RpmArg.lean](LeanDa/RpmArg.lean)). Position binding does not use it. For code binding, the adversary followed by the verification, its proof carrying the argument's proof, the adversary's transcript and the verdict (`advV`), is the code-binding adversary of a virtual oracle-free argument that reads the verdict (`psV`), whose extractor runs the argument's on the proof and the transcript (`extV`): the straight-line proof below applies to it, the challenges of the root inserted unused before the climbs (`run'_bind_const`, by the commutation of independent computations in the random-oracle model, `Common.run_bind_bind_comm`), and its knowledge-soundness term is the statement's knowledge-soundness game of the code-binding adversary itself, its transcript logged (`ksB`, `relabel_ksGame`).

**How the proofs reach this model.** Through the two-oracle random-oracle model (`H` a random oracle, the challenges' duplex over an independent random function `F`), by `common`'s indifferentiability of the sponge with the duplex's direct permutation calls (`Common.keccak256_transfer2`, `Q² / 2^508`), and from there to Wagner's theorems ([below](#wagners-theorems-the-step-before-the-random-permutation-model)), which are steps of the proof.

Position binding is a concrete bound: after the transfer, a win gives two openings that verify for the hash function of the final random-oracle cache, so the climbs' inputs, all cached, contain a collision (`posBindingPost_win`, by `openingsCollision_spec`), which `Q` hash calls find with probability at most `Q² / 2^256` (`prob_hCollision_le`).

### Code binding by a straight-line argument

The proof of `leanDa_codeBinding_rpm_bound` ([LeanDa/StraightTree.lean](LeanDa/StraightTree.lean), [LeanDa/StraightBad.lean](LeanDa/StraightBad.lean), [LeanDa/Straight.lean](LeanDa/Straight.lean), [LeanDa/StraightBound.lean](LeanDa/StraightBound.lean)) is built on Wagner's framework and games: his code-binding game, his reduction against the argument's knowledge soundness and his membership test's soundness. It replaces his forking lemma, which bounds the square of the advantage, by a straight-line extraction from the hash calls, so the test's soundness enters linearly.

* **One world for three verdicts.** After the transfer to the two-oracle model and the duplex lemma (the first step of the forking route below, `codeBindingExpRpm_le_G`), `H` and the challenges `G` are random oracles. After the adversary and the challenges of its root, the straight-line verdict (`tailH`) commits to the extracted matrix `w` with `H`; when the proof verifies and `w` satisfies the relation, it is whether `w` is not a codeword, or else whether the first opening that disagrees with `w` verifies. With `H` sampled as a table (the second step below, for any verdict: `idealT_evalDistEq`), a code-binding win is a knowledge-soundness break or a true verdict (`postP_imp`), so `Pr[code binding] ≤ Pr[knowledge soundness] + Pr[verdict]` (`prT_cbIdealG_le`), the knowledge-soundness term read back in the random-permutation model as below (`ksIdealG_le`, `rom2_le_ksExpRpm`).
* **A true verdict leaves a bad cache.** In the world with `G` one random oracle of vectors and both oracles lazily sampled, a cache is good (`Good`) when `H` is injective on its inputs and every matrix whose commitment's inputs are all cached, which commits to a root with cached challenges and passes the membership test on them, is a codeword. A coin-free run is read off its final cache (`replay_of_mem_support`), so the verdict's commitment and opening have their inputs cached (`commitCellsM_some`, `verifyCellM_some`): in a good cache `w` is a codeword, and an opening that verifies against `w`'s root opens `w`'s cell (`verifyCell_agree`), so the verdict is false (`not_good_of_tail`).
* **The bad events.** A fresh answer of `H` spoils a good cache only if it equals a cached answer (a collision), a 32-byte block of a cached input or of its own query (`chunks`: a node's children, a row's cell digests), or a root with cached challenges (`good_insertH`): every input of a commitment but the root's hashes to a block of another of its inputs (`commitIn_parent`), so a tree that a fresh answer completes had its root's challenges drawn before. That is at most `65 N` values among `2^256` for a cache of fewer than `N` entries. Fresh challenges spoil it only if the one matrix committed to their root (`commit_unique`), fixed before they are drawn, is not a codeword and passes: at most `14 / 2^192` (`checker_sound`, `prob_insertG_le`). By the bad-event budget with two weights (`prEvent_run_bad_le₂`), a bad cache has probability at most `N · 65 N / 2^256 + Q_G · 14 / 2^192` (`prob_not_good_le`), for at most `N = 2 Q + 2^20` queries of `H` and `G` (the adversary's, the challenges' and the verdict's: `isWeightBound_advSim`, `isWeightBound_tailV_hg`) and `Q_G = Q + 14` of `G` (`codeBindingExpG_le`).
* **The bound.** The transfers and duplex lemmas of both games and the collision term fold into `(Q + 2^22)² · 2^-247`, the test's term into `(Q + 2^22) · 2^-188` (`straight_rest_le`); the bound is below the forking route's for every `Q` (`straight_le_fork`).

### Wagner's forking route

Wagner's forking route (`leanDa_codeBinding_rpm_fork`, the proof of the end statement before the straight-line one) goes from the two-oracle ROM to Wagner's game in three steps.

* **The challenges are a random oracle of the roots, up to capacity collisions** (the duplex lemma, `Common.Duplex.duplex_le`, instantiated by `daDuplex` in [LeanDa/RpmDuplex.lean](LeanDa/RpmDuplex.lean)). The challenges' sponge over `F` is a duplex: the label's hash seeds the first state, absorbing the root writes its words over the rate, each sample permutes with the rate zeroed, and every step keeps lanes `16 … 24`, the 576-bit capacity. The adversary's direct calls of `F` are answered by a simulator from `H` and a random oracle `G` of the roots, programming a fresh call on a challenge path with `G`'s challenge and uniform other bytes. Unless two of the at most `Q + 15` states share a capacity (probability at most `2 (Q + 15)² / 2^576`), the challenges the verifier derives are `G`'s ([LeanDa/RpmCodeBinding.lean](LeanDa/RpmCodeBinding.lean), `codeBindingExpRpm_le_G`; the verifier's recomputations of the challenges hit the cache, `prob_codeBindingPost`).
* **`H` is sampled in advance on short strings.** Every string the verifier hashes has at most 2048 bytes (a cell's), so `H` is sampled as a uniform table `h` on those strings and lazily elsewhere. For each `h`, the simulated world is Wagner's code-binding game for LeanDA with the hash `Hh h` against the adversary `advH h` (the simulated adversary, `H` answered from `h` and lazily on long strings, at most `Q` challenge queries) ([LeanDa/RpmWagner.lean](LeanDa/RpmWagner.lean), `cbIdealG_evalDistEq`, `prT_gameW`).
* **Wagner's bound for each `h`, averaged.** `leanDa_codeBinding` holds for each `h`; averaging the squared bound over `h` (Cauchy–Schwarz, `sq_tsub_avg_le`) gives the same bound with each term replaced by its average over a uniformly random `H`.

Wagner's three terms are then bounded, each by its own argument.

* **The collision terms are birthday bounds** ([LeanDa/WpbBound.lean](LeanDa/WpbBound.lean), [LeanDa/ForkBound.lean](LeanDa/ForkBound.lean)). Wagner's two reductions compute with the table `h` of `H`; transcribed with `H` as queries (`advX`, `wpbX`, `forkZ`, and the Merkle trees over an oracle, [LeanDa/MerkleM.lean](LeanDa/MerkleM.lean)), each is a computation answered by `h`, and sampling `h` in advance is sampling it lazily, so a collision among its `N` hash calls has probability at most `(N + 2)² / 2^256` ([LeanDa/Birthday.lean](LeanDa/Birthday.lean), `prob_collision_le`). The forking reduction runs the adversary twice with the same `h`: the replay fork commutes with answering `H` by a fixed function ([LeanDa/ForkCollapse.lean](LeanDa/ForkCollapse.lean), `contextFork_collapse`), and VCVio's bound on the fork's queries doubles the run's. With `r ≤ 1024` rows, `N ≤ Q + 2^19` for weak position binding and `N ≤ 2 Q + 2^21` for the fork.
* **The knowledge-soundness term is the argument's knowledge soundness in the random-permutation model** ([LeanDa/KsRpm.lean](LeanDa/KsRpm.lean)). Wagner's reduction against knowledge soundness, averaged over `h`, is the simulated world of an adversary that runs the code-binding adversary and reads the challenges of its root (`ksIdealG`, `prT_ksExpH`); the duplex lemma, reversed (`Common.Duplex.duplex_ge`), and the two-oracle transfer read it back in the random-permutation model as the knowledge-soundness experiment `ksExpRpm` of the adversary `ksAdv A`, which computes the challenges by the deployed duplex over `π` (`ksIdealG_le`, `rom2_le_ksExpRpm`), at most `Q + 2^22` permutation calls with the relation's commitment.
* **The forking lemma's square root**: Wagner's bound is `(P − T)² ≤ (Q + 2)(ε₂ + δ)`; with `ε₂ ≤ (2x)² / 2^256` for `x = Q + 2^20`, the arithmetic and geometric means give `P ≤ T + x / 2^95 + x² / 2^159 + (Q + 2) / 2^94` ([LeanDa/Arith.lean](LeanDa/Arith.lean), `fork_sq_le`), and the remaining terms fold into `(Q + 2^20) · 2^-93 + (Q + 2^22)² · 2^-158`.

## Wagner's theorems, the step before the random-permutation model

Benedikt Wagner's theorems for the generic construction, instantiated with LeanDA. They hold for every hash function, with the membership challenges a random oracle from roots to `E^14` (his model), and the random-permutation binding theorems above are proved from them (completeness from the core of his completeness proof, `PqDas.honest_verify`). For `r` rows, any hash `H` (the crate's is Keccak-256), an argument `ps` for `Relation r H` and its extractor `ext`:

| Theorem | Statement |
| --- | --- |
| `leanDa_positionBinding` | `Pr[position binding] ≤ Pr[collision of H]` for the explicit reduction `merkleCollider r H (posBindingReduction ps A)` |
| `leanDa_codeBinding` | `(Pr[code binding] - (ε_ks + ε₁))² ≤ (Q + 2) (ε₂ + 14 / 2^192 + 2^-2688)` for an adversary making at most `Q` random-oracle queries |

In the code-binding bound `ε_ks` is the success of the reduction `ksReduction` against the knowledge soundness of `ps`, and `ε₁`, `ε₂` are the successes of two explicit reductions finding collisions of `H`. `14 / 2^192` is the membership test's soundness and `2^2688 = |E|^14` the number of its challenges.

They rest on what this project proves about LeanDA's building blocks ([LeanDa/Security.lean](LeanDa/Security.lean)):

* `checker_complete`, `checker_sound`: the membership test accepts every codeword for every challenge, and a fixed matrix that is not a codeword for at most a `14 / 2^192` fraction of the challenges `z ∈ E^14`. This is Proposition prop:rs-membership of `doc/leanvm` Annex D: the additive Reed-Solomon code at rate one half is its own dual on the crate's domain (`orthogonal_rsCode`, by Lemma lem:domain-sum and Corollary cor:rs-dual), the dual codeword is the encoding of the tensor `⊗_j (1, z_j)` in the novel basis (`dual_eq_sum`), and the inner product with a row that is not a codeword is a nonzero multilinear polynomial of total degree at most 14 in `z`, so Schwartz-Zippel applies (`card_acceptSet_le`).
* `merkleVC_perfectlyComplete`, `posBindingExp_le_hashCollisionExp`: honest cell openings verify, and two openings of one cell to different values give a collision of the hash, which `merkleCollider` computes. Both hold for every hash function, as do the theorems.

## Assumptions

* **An argument of knowledge** for LeanDA's relation (`RelationRpm`, `relationM`: the cells commit to the root and pass the membership test on the root's challenges, drawn by the deployed duplex), its prover and verifier querying the random-permutation model's oracles (`NarkRpm`): perfect completeness for every permutation for `leanDa_perfectlyComplete_rpm`, and knowledge soundness in the random-permutation model with a straight-line extractor reading the adversary's transcript (`ksGame`) for `leanDa_codeBinding_rpm_bound`, its hypothesis. Wagner's theorems for any `H` keep his oracle-free argument (`Nark`, for `Relation`, the statement carrying the challenges); its extractor `ext` runs inside his two collision reductions, whose terms are birthday bounds here for every `ext` (the reductions' hash calls are counted, `ext`'s computation is not a hash call). Discharging this assumption with leanVM, the aggregation guest proving the relation, is not done here: leanVM's verifier's Fiat-Shamir transcript would need to be domain separated from the challenges' duplex, and its knowledge soundness (`lean_vm`) is stated with an extractor whose running time is not part of the statement.
* **Collision resistance of the hash**, through the explicit reductions. The theorems hold for every hash function `H`, so they are reductions, not bounds; LeanDA's is Keccak-256 (Ethereum's), which `lean_vm` defines and checks against the Rust.
* **The random-permutation model** (the RPM theorems): Keccak-f[1600] behaves as a uniformly random permutation.
* **The random-oracle model for the challenges** (the ROM theorems). The crate derives `z` with a duplex sponge over Keccak-f[1600], seeded with the hash of the label `leanDA/rs-membership/v1`, that observes the root's four words as two scalars and samples `14` times (`membership_challenges`); Wagner's game models this as one random oracle from roots to `E^14`. The RPM theorems derive the challenges by the deployed duplex instead.

## The model and the Rust code

The scheme is in [`Statement/LeanDa.lean`](../Statement/LeanDa.lean) with the definitions of Wagner's framework the end statements need (consistency of opened cells), arguments with oracle access (`NarkRpm`) and the end statements themselves (`LeanDa.PerfectlyCompleteRpm`, `PositionBindingRpm`, `CodeBindingRpm`); `LeanDa/Scheme.lean` and `LeanDa/Defs.lean` keep what only the proofs use (LeanDA's vector commitment and code checker, Wagner's relation and verifier with an oracle-free argument, the challenges' duplex, Wagner's terms over a random table of `H`), and `PqDas` the rest of Wagner's framework (`PqDas/Defs.lean`: his oracle-free arguments `Nark`, vector commitments, code checkers, his reductions; the erasure code commitment, the random-oracle runtime and the scheme, through which his theorems are stated). The scheme cites the crate at leanVM's `main` branch, commit `4af2cdddd`. It is checked by reading both sides; it is not a mechanized refinement of the Rust.

* **The code.** A row's `2^14` payload symbols are the values of a polynomial of degree below `2^14` on the domain points `0 … 2^14 - 1` (the element of `K` whose bits are `b` is point `b`, the span of `e_c = x^c`), and its codeword is that polynomial's values on the `2^15` points. The crate computes these maps with the inverse and forward additive NTT; the model uses the maps themselves, so the NTT's correctness (Annex D, Proposition prop:ntt) is not mechanized here. The dual codeword is `∏_j (1 + z_j Ŵ_j(x))`, which `dual_eq_sum` shows is the encoding of the tensor that `dual_codeword` transforms; `dualCodeword_eq_dual` proves the transcribed `dual_codeword` computes it.
* **The matrix.** The row count `r` is a parameter; the crate accepts `1 ≤ r ≤ 1024` and the theorems hold for every `r ≥ 1`. The erasure code's positions are the `128 r` cells of the `r` rows, the cells sampling opens. The commitment pads the rows to `2^⌈log₂ r⌉` with zero codewords and hashes the padded matrix, as `commit_codewords` does.
* **Openings.** The crate keeps the column tree for answering samples but verifies none. An opening is modelled as the cell's path in the column tree, of the tree's height, with the row root; it verifies when the path climbs to a column root that hashed after the row root gives the commitment.
* **The deployed algorithms.** `Scheme.lean` also transcribes, computably on lists, the crate's commitment (`commitCodewords`, each tree built level by level), the challenges' duplex sponge (`Sponge`, `verifier/src/transcript.rs`, and `membershipChallenges`), the membership vector by the additive NTT (`membershipVector`, `verifier/src/da.rs`) and its digest, the hash of the hashes of its `128` columns of `2^8` entries (`vectorDigest`). The hash `H` and the sponge's permutation `P` are parameters; the crate's are Keccak-256 and Keccak-f[1600]. [LeanDa/Commitment.lean](LeanDa/Commitment.lean) proves the commitment is the model's: for every hash `H` and codewords of `2^15` symbols, `commitCodewords H rows = commitCells H (cellsOfRows rows)` (`commitCodewords_eq_commitCells`). `membershipVector_eq_dual` proves that `membershipVector` computes the model's `dual` at the challenges.

The aggregation node's DA claim (`Statement/LeanVmGuest.lean`) is stated with these definitions, on leanVM's Keccak-256 and Keccak-f[1600]; `lean_vm`'s node vectors check `commitCodewords` and the membership vector's digest against the crate's.
