# Statement

What the repository proves, in the files a reviewer reads: definitions and end statements only,
one Lake package (`statement`) of twelve files, `Statement/<Name>.lean` (Lean modules
`Statement.<Name>`), the leanISA guest program's generated bytecode in [`Data/`](Data/), and, for
speed only, proved `@[csimp]` lemmas in [`Fast/`](Fast/), which a reviewer need not read, nor the
theorems the extractor's decoder takes as proof fields, in [`Decode/`](Decode/), nor the honest
prover's definitions, in [`Prover/`](Prover/) (below). It imports Mathlib,
VCVio and CompPoly and nothing else (CI checks it); every other project of the repository is proof
and imports it.

**The model.** Every end statement with an adversary is in the random-permutation model: one
uniformly random permutation `π` of the 1600-bit Keccak state, which every party queries forward
(`π x`) and inverse (`π⁻¹ y`), Keccak-256 the sponge over `π` and Keccak-f[1600] `π` itself. That
the deployed Keccak-f[1600], a fixed permutation, behaves as a random one is the assumption.
`Statement/` contains no random oracle: the random-oracle model and the sponge's
indifferentiability, through which the proofs pass, are proof steps, and their definitions
(the two-oracle and duplex simulators, Wagner's reductions and his random-oracle terms) are in
`common` and `lean_da`. LeanDA's code binding is conditional on the argument's knowledge
soundness in the random-permutation model, the only term of its bound that depends on the
argument.

**The sources.** The leanVM definitions are transcribed from leanVM at
`94ee12ff6b2a3d42ba8328e22d09443692e4800b` (branch `main`, [`../leanvm-rev`](../leanvm-rev)): each
cites its source (`verifier.py:N`, `*.rs:N`, `doc/leanvm` sections). LeanDA's security framework is
Benedikt Wagner's ([b-wagn/fv-pq-da](https://github.com/b-wagn/fv-pq-da), Apache-2.0, see
[`../lean_da/NOTICE`](../lean_da/NOTICE)).

## Reading order

1. [`RandomPermutation.lean`](RandomPermutation.lean): Keccak-f[1600] as leanVM computes it
   (`keccakF`, on `KState`, `25` lanes of `64` bits: the one state type of the statement) and
   Keccak-256 over any permutation of the state in any monad (`KeccakHash.keccak256With`), the
   deployed one over Keccak-f[1600] (`keccak256`); the random-permutation model (`permSpec`: `π`
   and `π⁻¹`; `lazyPerm`, the lazily sampled uniform permutation); a cost bounded on every path
   (`IsWeightBound`); the oracles of the model (`KSpec`: coins, Keccak-256, `π`, `π⁻¹` on
   `KState`), a game's cost in permutation calls (`permCalls`) and its run against the lazy
   permutation, Keccak-256 the sponge over it (`runK`); the SUF-CMA game of a hash-based
   signature scheme in the random-permutation model (`SufCma.rpmGame`, `rpmExperiment`) and its
   security notion (`SufCma.RpmSecure`).
2. [`LeanXmss.lean`](LeanXmss.lean): what leanXMSS and leanSPHINCS share (the tweakable hash's
   types, bytes and address, `crates/signatures/src/tweak.rs`; a hash chain, a Merkle path's fold
   and a Merkle tree's node, `walkChain`, `foldPath`, `buildTree`, which every chain, fold and tree
   of both schemes instantiates), the leanXMSS scheme and
   `LeanXmss.Rpm.LeanXmssRpmSecurityStatement` (`RpmSecure` at 127 bits).
3. [`LeanSphincs.lean`](LeanSphincs.lean): the leanSPHINCS scheme (on the shared part, exported
   into `Sphincs`; one tree, its signature the randomizer, the forest opening, the WOTS+C counter
   and chain values and the path) with the deterministic signer, the proved lifetimes, and
   `Sphincs.Lifetimes.RequestedSecurityRpm` (`RpmSecure` at 127 bits at each lifetime).
4. [`Field.lean`](Field.lean): `K = GF(2^64)` (CompPoly's `BF64`), `E = GF(2^192)`, the generator
   `g`; Keccak lanes, bytes and digests as field elements.
5. [`LeanDa.lean`](LeanDa.lean): LeanDA (fields, Reed–Solomon rows, the Merkle commitment, the
   membership test), the parts of Benedikt Wagner's framework the end statements name (the
   consistency of opened cells), the relation of LeanDA's argument (the root's challenges drawn by
   the deployed duplex over a permutation), arguments that query the model's oracles, the
   commitment and the challenges' duplex over a permutation, LeanDA's games in the
   random-permutation model, where the adversary, the argument (`NarkRpm`, its extractor reading
   the adversary's transcript) and the verifier query the same oracles (`KSpec`; position
   binding, code binding, the argument's knowledge soundness `ksGame`, completeness for every
   permutation `π`), and `LeanDa.PerfectlyCompleteRpm`,
   `LeanDa.PositionBindingRpm`, `LeanDa.CodeBindingRpm`. Code binding is conditional: if the
   argument is knowledge sound in the random-permutation model with error `(q + c) · 2^-k`, LeanDA
   is code binding with error `(Q + c + 2^22) · 2^-k + (Q + 2^22) · 2^-188 + (Q + 2^22)² · 2^-247`
   for every `Q` and `r ≤ 1024` rows (a straight-line proof on Wagner's framework); the last
   term passes 1 at about `Q = 2^123.5`. `CodeBindingRpm`'s docstring says which arguments satisfy
   the hypothesis.
6. [`LeanIsa.lean`](LeanIsa.lean): leanISA (memory, the six instructions, programs, one step, `run`,
   `ValidExecution`: a run from the initial state `(pcInitial, fpInitial)` that halts in the final
   state `(pcFinal, fpFinal)`, the instruction counts `Trace.count`, the bytecode encoding, the
   bytecode table the verifier reads, `bytecodeWords`, and the public input's digest, `publicDigest`, with
   its inverse, `PublicInput.ofDigest`), and a
   program assembled from compiled functions (`CompiledFn`, `assemble`).
7. [`LeanVmVerifier.lean`](LeanVmVerifier.lean): the verifier, `python-verifier/verifier.py`
   transcribed section by section, for any hash function and permutation in any monad
   (`verifyWith`), with the WHIR constants it reads, the Keccak GKR reduction, the Fiat-Shamir
   duplex over Keccak-f[1600], the deferring verifier an aggregate runs on its children, and the
   sizes a stream announces (`announced`). Where the transcription's form differs from the pin's
   without changing what it computes, its docstring gives the pin's lines and why the two agree.
8. [`Extractor.lean`](Extractor.lean): the knowledge extractor, straight-line, deterministic and
   computable, with running time polynomial in the announced committed size `2^μ` and the number
   of evaluations, not in the proof's size, and infeasible at deployed sizes (its cost table, read
   off its loops, not proved): from the proof and the adversary's Keccak-256 evaluations, the
   announced sizes and the stack's root, the committed word (the Merkle tree inverted through the
   evaluations), its Johnson list (at most `2^18` stacks, listed by CompPoly's Guruswami–Sudan list
   decoder over `GF(2^64)` and pruning across the lanes), and the halting run of a candidate's
   memory image within the announced tables' rows that is a valid execution, if there is one.
9. [`LeanVm.lean`](LeanVm.lean): a statement (a program and a public input), the verifier on it
   (`verifier H F`), its calls as oracle queries (`HashSpec`), the honest prover's type and **the
   honest prover**, `prover` (`LeanVM.Prover.prove` of [`Prover/`](Prover/) with the oracle calls),
   the committed size; the random-permutation experiment (`rpmExperiment`: an adversary with private
   coins, `RpmAdversary`, its queries to `π` and `π⁻¹` counted by `permQueries`, its `Transcript`;
   `rpmRun`, the same with any computation in place of the verifier), the extractor on the
   transcript (`extractorRpm`, on the Keccak-256 evaluations the transcript holds,
   `transcriptPaths`), **`LeanVM.KnowledgeSoundness`, `LeanVM.Completeness`**.
10. [`LeanVmGuest.lean`](LeanVmGuest.lean): the leanISA guest program's specification (aggregation):
    DA claims, a node's statement, its digest (Keccak-256 of a preimage), witness and relation
    (`NodeRel`: leanXMSS and leanSPHINCS claims, DA claims, children verified by the deferring
    verifier, the batching of their deferred claims), a decoder and what a proof of the leanISA
    guest program establishes with it (**`GuestKnowledge`**), the candidate collisions of two
    statements' digests and **`LeanVM.Node.DigestBinds`** (a digest binds the seed and a statement
    of a given shape, up to a Keccak-256 collision), the deployed leanISA guest program
    (`LeanVM.Guest.guest`, from [`Data/`](Data/)), its deployed limits (`Limits`, `CapsAgree`,
    `NoZeroChallenge`), **`LeanVM.Guest.Budget.GuestCompleteCovered`** (the nodes `Covered` lists), the honest proof as a child (`verifierNZ`, `atKeccak`, `ChildOk`,
    **`GuestChildComplete`**); and the recursion step: the batching of the children's claims as a
    verifier program (`batchAny`, run from the batching's seed by `batchVerifier`), an adversary's
    proof run through it in the random-permutation model (`LeanVM.Rpm.rpmRun`, `LeanVm.lean`), the
    event that it accepts children with a false claim (`FalseChildren`), the program's query bound
    (`batchQueryBound`), and **`LeanVM.Guest.Batch.BatchSound`**: the batching run outside the
    circuit with Keccak-f[1600] = `π`, which does not compose with the guest program's in-circuit
    statements (their `KECCAK` is the deployed Keccak-f[1600]), so soundness across recursion levels
    does not follow from it.
11. [`Theorems.lean`](Theorems.lean): every end theorem, as the fields of `Statement.Theorems`.
12. [`Corollaries.lean`](Corollaries.lean), optional for review: statements that follow from
    `Theorems` alone, in their composed form (`lean_vm` proves `Theorems decode → Corollaries
    decode`): what an accepted proof of the leanISA guest program establishes
    (`LeanVM.Node.AggregateSound`, with `Explains`: `KnowledgeSoundness`, `GuestKnowledge` and
    `DigestBinds` composed) and the completeness on recursion nodes and leaves
    (`GuestCompleteRecursion`, `GuestCompleteLeaf`, the first two families of `Covered`).

[`Data/`](Data/) is the guest program's compiled bytecode, generated from leanVM's sources by
`lean_vm/scripts/guest-export` (do not edit; `guest-export --check` fails when it is stale, as CI
runs it). It needs no review beyond that check.

[`Fast/`](Fast/) makes the compiled definitions fast and changes nothing they mean: `@[csimp]`
lemmas, each proved, that compile `GF(2^64)` products on machine words (`FieldWords`), the
degree-three extension's product unrolled (`CubicExt`), Keccak-f[1600] with its lanes written
out and Keccak-256 without the monad, its blocks read from arrays (`Keccak`), and the signature
schemes' verifiers with a constant-depth lookup (`Schemes`). A `@[csimp]` lemma acts where a definition is compiled, so they are here, imported by
`Field.lean`, `LeanDa.lean` and `LeanVmGuest.lean`, for the statement's own compiled definitions
(the verifier, the guest program's specification, LeanDA) and every module after them. They need no
review: a `@[csimp]` lemma is an equation the kernel checks.

[`Prover/`](Prover/) is leanVM's honest prover as an executable program, `LeanVM.Prover.prove H F
prog input t ρ fuel` (`Prove.lean`), for a hash `H` and a permutation `F` in any monad: with the
oracle calls it is the prover `LeanVM.prover` that `Completeness` and `GuestChildComplete` name,
and with Keccak-256 and Keccak-f[1600] in `Id` it is `lake exe leanvm-prove`, whose proofs the
Rust and Lean verifiers accept (`lean_vm/README.md`). It is definitions only: the witness from the
trace (`Witness.lean`, `Columns.lean`: one run of the program; the empty proof unless the trace is
a valid execution within `2^28` committed cells), a script of the prover's moves (`Script.lean`)
for each phase of the verifier (`Ntt.lean`, `Bus.lean`, `Gkr.lean`, `Table.lean`, `Public.lean`,
`Keccak*.lean`, `Ring.lean`, `Whir.lean`; `Mle.lean`, `Sumcheck.lean`, `Code.lean` their helpers),
and its run against the verifier's own program (`Run.lean`: the challenges squeezed from the
sponge, each Merkle tree built once, the proof-of-work nonce searched among the first `fuel`).
Its correctness is proved (`lean_vm/LeanVM/Prover/`: the prover's proof is, at every hash and
permutation, the proof of the honest strategy the completeness proof follows, at the execution's
own witness), so a reviewer need not read it line by line; a reviewer checks only that it is a
genuine prover: it computes its proof from the execution, its only search is the nonce search
bounded by `fuel`, and it branches on no hash or permutation answer other than through the
challenges the verifier's program samples (`Run.lean` gives the script nothing else).

[`Decode/`](Decode/) holds the two facts about `GF(2^64)` that the extractor's root finder takes as
proof fields (the trace `Σ z^(2^i)` lies in `{0, 1}` and separates elements on the basis `x^i`),
and the facts about `K.ofBits` they rest on. It holds theorems only
(`lean_vm/tests/LeanVMTests/Extraction/DecodeProps.lean` checks that every constant it declares is
a proof), so nothing in it can change what the extractor computes or what a statement says: it
needs no review.

A few definitions carry proofs, which are here because the definitions need them: the extractor's
decoder contexts (CompPoly's contexts bundle their correctness proofs: `traceCtx`, `gsContext` in
`Extractor.lean`); and decidability instances.

Each project's root module (`lean_vm/LeanVM.lean`, `lean_xmss/XmssSecurity.lean`,
`lean_sphincs/Sphincs.lean`, `lean_da/LeanDa.lean`) is its end file: it checks that each end
theorem proves its statement and pins its axioms to Lean's three (`propext`, `Classical.choice`,
`Quot.sound`). The guest program's two soundness statements take the decoder as a parameter; the end
theorems name `LeanVM.Guest.End.decode` ([`EndFinal.lean`](../lean_vm/LeanVM/Guest/EndFinal.lean)),
which reads the witness off the execution's memory. Their content is in that decoder: one that chose
another statement of the same digest would satisfy `AggregateSound` (`Corollaries.lean`) through a
Keccak-256 collision.

## Building

`lake build` here builds the twelve files, the data, `Fast/`, `Decode/` and `Prover/`; the other projects
build it as a dependency. The data's modules are heavy: `python3 -I ../lake-build.py .` builds them
in one `lake build` that admits its modules by memory, as CI does.
