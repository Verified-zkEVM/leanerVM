# End-to-end knowledge soundness of leanVM aggregation — framework draft v3

(History: `design-v1.md`, `design-v2.md` in this directory; paper `ePrint 2023/1646`, text
the paper; repo `lean_vm`, guest source
`.leanvm/crates/rec_aggregation/guests/lean_ethereum.py`.)

## Goal
Lean theorem, Lean's three axioms, about the deployed aggregation (recursive, unbounded depth):
no adversary making ≤ Q oracle queries gets an aggregate accepted that claims a leanXMSS/leanSPHINCS
signature on a message the honest key holder never signed (or a DA claim not backed by data),
except with probability ε(Q) independent of depth and tree size. Stated first as knowledge (an
explicit extractor outputs valid witnesses for every claim of the tree), then composed with the
schemes' ROM unforgeability. Exactly one heuristic, outside Lean, stated on that game.

## Settled by rounds 1–2 (seven adversarial reviews)
- Byte-level random oracle H : Bytes → Digest (the existing ROM framework, leanVM's KS, `batch_rom`,
  lean_xmss / lean_sphincs ROM proofs all use it). Ideal compression would be a stronger, less
  supported assumption (the ISA exposes arbitrary t/f0/f1; BLAKE2 mode security is proved from an
  ideal block cipher, not an ideal compression function) and would re-base all ROM proofs.
- Deployed guest bytecode and deployed proof format, unchanged. No new guest, no protocol variant.
- No in-circuit table re-checks (fatal growth). Oracle consistency of the in-circuit hashing is
  checked once, at the top.
- Every bad event is ONE event over the oracle cache, charged per query (universal corollary of
  `romSound` via `final_ineq`, Rom/Final.lean:453; same for batching, collisions, termination).
- Every BLAKE2s compression in the deployed guest and verifier is standard unkeyed BLAKE2s-256
  (RFC 7693): chains from the parameterised IV, no keyed/tree modes, no intermediate output used
  except as the next chaining value.

## The idealized system I(H)
1. V° (one program per statement): `verifyExecution` with the bytecode value `.computed` and the
   Flock lincheck terminal `require` (Spec/Verifier.lean:1990) deleted. Lemmas: `verifyDeferred c`
   accepts ∧ c's bytecode part true ⇒ V° accepts (identical transcript, the values are not
   absorbed); deployed `.computed` acceptance ⇒ V° acceptance. Root: `OuterChecks°` = DA digests ∧
   bytecode part of `DeferredClaim.Holds` (matrix part dropped). With Flock blind, its zerocheck and
   lincheck carry no checks; ring switching still adds one claim to the stacked opening (bound
   after all claims are fixed); the BLAKE2S table's 18 limbs live in `q_flock` and reach memory only
   through the bus (`flushesBlake2s`, Verifier.lean:1079); nothing else shares that region.
   Padding rows stay pinned to the concrete `paddingInstance` by the bus (Verifier.lean:1137-1146)
   and are excluded from the oracle check.
2. Table consistency (active rows only): a standard chain of a message x (length ℓ, k =
   max(1, ⌈ℓ/64⌉)) is rows r₁…r_k with r₁.cv = paramIv; r_{i+1}.cv = r_i.out; for i < k: block i of x,
   t = 64i, f0 = f1 = 0; r_k: the last block zero-filled, t = ℓ, f0 = 0xFFFFFFFF, f1 = 0 (so
   64(k−1) < ℓ ≤ 64k, or k = 1 and 0 ≤ ℓ ≤ 64). Consistency: for every x and every standard chain of
   x in the table, x ∈ cache and cache(x) = r_k.out. Rows on no standard chain are free. (No
   uniqueness rule is needed: universal quantification over chains forces agreement.)
3. Acceptance of I(H) [OPEN, see Q1]: V°(root) ∧ `OuterChecks°` ∧ every node of the tree
   (extracted) has a consistent table.
4. Baked constants [OPEN, see Q4]: AGG_SEED (= concrete BLAKE2s(label), the batching start) and the
   DA padding digests: parameters of `batch` / LeanDA (small changes), or a prefilled oracle.
   `R1CS_DIGEST`, the IV cells, `MD_FINAL` need nothing. `NodeRel`'s seed: `fiatShamirIvWith H`.
5. The heuristic, on the no-forgery game: instantiating H by BLAKE2s in I(·) ⇒ the deployed system
   (Lemma D: deployed acceptance ∧ no compression collision among a node's rows ⇒ I(BLAKE2s)
   acceptance). Flock is not covered by the heuristic: its soundness is proved
   (`compress_of_holds`, FlockSpec.lean:247, with `knowledgeSoundness_holds`).

## Lean architecture (sizes from the round-2 Lean review)
- W0 (serial, first): split the semantic parts out of Guest Core/Logic/Exec so Data/Checked (640k
  generated lines, 375 kernel checks) stop depending on the BLAKE2S semantics; a `HashModel`
  typeclass for the guest proofs (Row check, intermediate `cmp`, `Hb`, `Known`, the chain law);
  generic `ValidExecutionWith` with today's names as abbreviations; Spec `…With H` functions
  (`NodeRelWith` with the child check in cache form, digests, batch start, DA padding in lean_da).
  ~1.5–2.5k.
- W1 (Protocol): row predicate in the arithmetization; Flock-blind KS for V° (Flock/ring-switch
  phases become doom pass-throughs via `Doomed.append`; `leanIsaInstance` takes the flock option);
  generalize `Statements.lean` / `Sound/Theorem.lean` over program/certificate families. ~3–5k.
- W2: B2 statements over HashModel (proofs symbolic already); B1 base hash layer and the concrete
  instance; mechanical threading (~330 files, `omit` hygiene under warningAsError). ~2–3k + threading.
- W3 (after W2): B1's `Runs`/`RunsTo` on an Option run tracking queries (cache form), Whir
  `climb`/`openOne` leaf lemmas. ~2–4k.
- W4a/b (after W2): B1 consumers (Sig + Digest; Da + Main + Whir caps/queries). ~2–4k.
- W5: universal corollaries; termination (Q3). ~2.5–4k.
- W6 (after W2): bytecode-only batching program/certificate, constant start, universal. ~1k.
- C5: the chain lemma from the run's rows + table consistency + the oracle instance of HashModel.
  ~0.6–1k.
- E: composition with lean_xmss/lean_sphincs (Q5). Unknown, likely several k.
- Final assembly, Lemma D, non-vacuity (cheap: the deployed honest prover queries the oracle on
  everything it hashes; with positive probability the oracle agrees with BLAKE2s there). ~1.5–2.5k.
Total ~18–28k lines + E. Critical path W0 → W2 → W3 → C5/W5 → assembly.

## Open questions for round 3
Q1. Acceptance of I(H). Options: (a) defined via the extractor, extraction preferring codewords whose
    trace is consistent (simple; but "an attack on I(H)" has no verifier algorithm; possible
    vacuity concerns); (b) an operational non-succinct verifier V_I receiving, per node, the full
    committed words (or the tables plus a binding check: the multilinear extension of the 18 limb
    columns at the table-sumcheck point equals the limb claims, then opened by WHIR), checking
    consistency natively, with children named by seed rows H(iv‖x_c) in the parent's table — but
    V_I must not natively verify the children's proofs (that would be "flattening", a different,
    stronger system). Which is right, and exactly how, without flattening?
Q2. Is the reduction to "one universal event over the cache" airtight when the tree's nodes are
    obtained by decoding (Johnson-list candidates fixed at commit time, `extract_take_eq`)?
Q3. Termination: (i) rank through the Fiat–Shamir chain (child's public input → child's seed →
    child's challenges → absorbed by the parent's batching → parent's statement digest; bad event:
    a query input contains, at O(1) fixed offsets, the 24-byte encoding of a later answer, ≤ Q²c/2^192);
    or (ii) the log time of a node's first commitment decreases along child edges, bad event a
    decoding prediction ≤ |ℓ|·L₀·2^28/2^256 per query. Which is correct and simpler? Is every child
    edge covered by the chain in (i) (what about a child with no batching contribution)?
Q4. Constants: parameters vs prefilled oracle — which keeps the final theorem meaningful and the
    composition with the signature schemes clean?
Q5. Composition to no-forgery: adversary model (leanVM's adversary has no coins and no signing
    oracle; theirs is unifSpec + HashSpec + signing), the signer's hidden oracle queries vs the
    extractor reading only the visible log, Digest vs BitVec 256 oracle types, multi-key hybrid,
    query accounting (a leanXMSS signature ≈ 2^24 queries), signer limits. Minimal clean plan?
Q6. Anything else that makes the final theorem false, vacuous, or not mean "no forgery".
