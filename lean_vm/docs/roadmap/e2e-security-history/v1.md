# End-to-end knowledge soundness of leanVM aggregation — formalization framework, draft v1

## Goal (from the project owner)
One simple Lean theorem: for the full end-to-end aggregation system (recursive, unbounded depth),
an adversary that produces an accepted root aggregate "knows" a valid witness for every claim:
a leanXMSS signature for every XMSS claim, a leanSPHINCS signature for every SPHINCS claim, a
blob opening for every DA claim — anywhere in the aggregation tree. As few assumptions as
possible; Lean's three standard axioms only (no `axiom`, no `sorry`); heuristics named and kept
outside Lean, ideally exactly one.

## What exists today (repo lean_vm, branch mumbai)
- `LeanVM.knowledgeSoundness_holds` (Protocol/LeanVM.lean, Spec/Statement.lean): leanVM's
  verifier, BLAKE2s modelled as a random oracle on byte strings (`HashSpec = Bytes →ₒ Digest`),
  knowledge-sound for adversarially chosen statements (program, public input) with a
  straight-line extractor `LeanVM.extract` that reads the oracle's query cache and the proof
  (deterministic, makes no oracle queries, defined with classical choice of a Johnson-list
  codeword). Error `soundnessError Q = (Q+13213)(2^-128 + 5(Q+13213)/2^256)`.
  Generic engine: `romSound` / `romSound_of_imp` (Protocol/Compile/Rom/*, EndToEnd/Sound/*) for
  any verifier program `Prog Bool` with a doom certificate; seedings `Seeds`.
- The aggregation guest (a leanISA program, compiled from leanVM's `lean_ethereum.py`):
  `guest_knowledge` (Guest/EndKnow.lean): every valid execution of the guest decodes (`decode`, a
  choice-free, verification-free reader of the memory) to (seed, statement s, witness w) with
  `NodeRel bytecode seed s w`: every claim of s is held directly (signature verifies / blob opens)
  or by a child (claim ∈ child statement); every child's proof is accepted by the deferring
  verifier `verifyDeferred` (fixed-polynomial claims deferred); the children's claims are batched
  into s's deferred claim.
- `AggregateSound guest LeanVM.extract decode` (Spec/Guest.lean): ROM statement for the root.
- `children_sound` (Guest/Batch/Children.lean): under the deployed seed, root's deferred claim true
  ⇒ every child's proof is accepted by the deployed `verify` and its deferred claim holds, or a
  batching challenge is bad. `batch_rom` (Guest/Batch/Rom.lean): the batching, as a verifier
  program, is sound in the ROM (byte-level oracle).
- leanISA's BLAKE2S instruction is ONE BLAKE2s compression (chaining value, message block,
  metadata t/flags), checked in the proof system by the "Flock" sub-argument (an R1CS of the
  concrete compression circuit, with deferred matrix evaluations). The guest computes byte-level
  BLAKE2s (Fiat–Shamir chain, Merkle nodes and 512-byte leaves, statement digests, signature
  hashing) as chains of compression instructions. Its `verify_sub` re-runs the child's verifier
  in-circuit, including verifying the child's Flock sub-argument.

## The gap
Recursion: the root ROM theorem gives the children's proofs (decoded), accepted by `verify`
computed with concrete BLAKE2s inside the guest. To extract a child's witness we need knowledge
soundness for that child's proof; but in a ROM where the native verifier's hash is a random
oracle, a proof verified in-circuit with concrete BLAKE2s is not a proof the oracle verifier
accepts (the model is inconsistent). Conditioning on "oracle = BLAKE2s on those inputs" is
vacuous.

## The proposed framework (after Chiesa–Guan–Samocha–Yogev, "Security bounds for proof-carrying
## data from straightline extractors", ePrint 2023/1646; PDF at ePrint 2023/1646)
Paper, informally:
- Thm 1: a relativized NARK (proves oracle computations) with a straight-line extractor
  (deterministic, oracle-query-free, reads the adversary's query-answer trace) yields PCD (by the
  canonical recursive construction) with knowledge-soundness error κ_PCD(λ,q,s,N) ≤ κ_ARG(λ,q,s'),
  s' = s + O(N·t_ARG); in the pure ROM, adversary size is irrelevant, so κ_PCD ≤ κ_ARG(λ,q),
  independent of depth and size N. Proof: one SNARK adversary runs the PCD adversary once, runs the
  extractor over the whole transcript, outputs the first non-compliant vertex's message/proof.
- §2.3: relativized SNARKs in the ROM don't exist [BCG24], but a "weak" (non-succinct) one does:
  (P2,V2) proves C^f via a non-oracle circuit C' that reads its oracle gates' query-answer pairs
  tr_C from the (augmented) instance; V2 checks the base proof and checks tr_C against f by
  querying. Straight-line extraction and error carry over. Recursively composing (P2,V2) gives a
  non-succinct PCD in the ROM, secure by Thm 1, which "idealizes" the deployed hash-based PCD.
  Single heuristic: the deployed hash-based PCD is as secure as this idealized ROM PCD.

Proposed instantiation for leanVM:
1. Generic PCD theorem (Lean, Protocol layer): for an abstract relativized NARK with a
   straight-line extractor in our ROM framework, and a tree-shaped compliance predicate, the
   canonical PCD extractor's failure probability ≤ κ_ARG(q). Paper's single-adversary reduction.
2. Idealized leanVM node NARK: leanVM where the BLAKE2S table is public (part of the instance /
   proof, non-succinct) and NOT constrained by Flock; intermediate chaining values free; the
   verifier reconstructs each compression chain (reject duplicate intermediate outputs, so chains
   are unique) and checks every final output equals H(message) with the byte-level oracle H.
   Straight-line KS from the existing proof (most sub-proofs reused; Flock dropped).
   Granularity: byte-level H kept (so the existing ROM framework is reused); the alternative,
   an ideal compression function f with native H = BLAKE2s-mode over f, would require re-basing
   the ROM framework (multi-block Merkle leaves, seed).
3. Idealized guest: the guest whose BLAKE2S rows are answered from its public table, and whose
   child verification drops the child's Flock check and instead reads the child's table and
   re-checks it against H in-circuit (rows added to the parent's table). Its correctness:
   the guest proofs (B1/B2) made parametric in what a BLAKE2S row returns, then instantiated.
4. Composition: decode + binding (collisions now statistical, all hashes are H) + batching
   (`batch_rom`, its hashes in-guest → oracle gates) ⇒ e2e theorem:
   Pr[root accepted ∧ the extractor does not output valid XMSS/SPHINCS signatures and DA openings
   for every claim in the tree] ≤ κ_leanVM(q) + batching + collision terms.

## Known worries (author's own)
- The formal theorem is about an idealized system that differs from the deployed one in the
  proof system (no Flock, public tables) and in the guest (child verification). Is that the right
  object? Is "deployed ≈ idealized" really one heuristic, as in the paper?
- Is the byte-level idealization with free intermediate chaining values faithful/sound?
- Size: phases 2–3 are large (guest proofs, protocol variant).
- Is there a cheaper or more faithful framework that yields the same final theorem?
